## 约定：博客仓库在哪，怎么操作它

这个命令会在任何项目的会话里被调用，当前目录大概率不是博客仓库。

- 博客仓库：`/Users/baizhe/code/github/blog-source`（下文叫 BLOG，下文的 `source/...` 都相对 BLOG）。
- Bash 每次调用后工作目录会重置，所以每条涉及 BLOG 的命令都以 `cd /Users/baizhe/code/github/blog-source` 开头，或用 `git -C` 和绝对路径。
- 命令被钩子改写时（`rg` 报 `grep: invalid option`，或 `find` 输出里夹着 `rtk:` 提示），把命令名换成 `"$(command -v rg)"`、`"$(command -v find)"` 这种写法，参数不变，就能绕过。
- 找不到 `hexo` 时（新开的 shell 里常见）：`export PATH="$HOME/.nvm/versions/node/$(ls ~/.nvm/versions/node | tail -1)/bin:$PATH"`。
- BLOG 的规范和我积累的反馈记忆在其他项目的会话里不会自动加载。动手前先读完这两份，写作规范以它们为准，下文不再重复：
  1. `/Users/baizhe/code/github/blog-source/CLAUDE.md`
  2. `/Users/baizhe/.claude/projects/-Users-baizhe-code-github-blog-source/memory/MEMORY.md`，再按索引读记忆文件：写作类反馈（风格、句子、结构、渲染坑）每次都读，放置类规则只在灵感涉及对应主题时读

## Step A：灵感路由，决定落在哪

完成标准：写出 A4 的路由结论（落点、理由、备选）。

### A1 提炼灵感

从灵感文字和当前会话里提炼：

- 一句话主题
- 关键词：中文、英文、同义词、工具名都列上（"任意跳转"要同时想到 jump、easymotion、flash、leap）
- 内容性质：概念 / 操作步骤 / 踩坑 / 对比选型 / 速查
- 预估篇幅：一两句 / 一个小节 / 一整篇
- 会话里跑过的命令和输出：写成"实测"之前，在博客环境或临时目录重新跑一遍；本机没有这个工具时不安装，文中标明"未实测"和适用的版本范围，总结里也说明

灵感来自其他项目的会话时，内容可能夹带真实业务信息。博客示例用虚构的通用领域（图书借阅、订单这类），真实的表名、字段、接口、产品名、价格、邮箱一律留在原项目里。

### A2 查重，同时找落点

`tldr.md` 和 `hello-world.md` 含大段 base64，搜索时排除它们。

```bash
cd /Users/baizhe/code/github/blog-source
# 1. 关键词命中了哪些文章
rg -l -i -g '!tldr.md' -g '!hello-world.md' "关键词1|关键词2" source/_posts blog-ideas.md

# 2. 所有文章标题，用来判断主题归属
rg -n "^title:" source/_posts --glob '!tldr.md' --glob '!hello-world.md'

# 3. 候选文章的章节结构，用来定位具体放哪一节
rg -n "^#{2,3} " "source/_posts/候选文章.md"

# 4. 历史上写过又被删掉的内容
git log --oneline -S"关键词" -- source/_posts
```

关键词要具体：一次搜索命中超过 10 个文件，说明词太泛，换成更具体的词组再搜。"没写过"的结论要满足两条：中文、英文、同义词三组说法各搜过一遍；每个候选文章里相关段落读过原文，不只看标题。

### A3 决策规则

按顺序判断，命中就停：

1. 已经写过：灵感的内容已被已有文章覆盖，哪怕文章还能再扩展也算写过。把它所在的文章和章节告诉我，可扩展的点写进备选，然后结束。
2. 写过但有错或过时，或者灵感里有已有文章没覆盖的信息：当作"并入已有文章"，改那一节。
3. 记忆里有现成放置规则：直接照做（例如原生 Vim 的写进 vim 基本操作的"常见操作场景"；Neovim/LazyVim 配出来的写进 neovim 那篇，写简略；内容多就单独成篇，并在 vim 那篇加链接）。
4. 并入已有文章，三条同时满足：已有主题对口的文章；新内容不超过一个小节；放进去不破坏那篇的主线。落到最相关的章节，没有合适章节就在它之后新增一个小节；几个章节都合理时，选内容性质最接近的（速查类内容进速查章节），其余写进备选。
5. 新建文章：没有对口主题，或内容超过一个小节，或放进去会破坏主线。新建后在主题最近的已有文章里加互相链接（按 CLAUDE.md 的系列文章约定和内部链接格式）；库里没有对口文章时选弱相关的，并在总结里说明。
6. 一个灵感里有几个相对独立的点：分别判断去向，可能一部分并入、一部分新建。
7. 拿不准：选最合理的往下走，备选写进结论。

### A4 宣布结论

每个点不超过三句话（含理由和备选），然后直接继续；灵感有多个点时逐点各写一条：

> 路由结论：并入《文章标题》的「章节名」（理由：……；备选：……）
> 或：新建《暂定标题》，并在《相关文章》里加链接（理由：……）

最后的预览总结里再写一遍，方便我不同意时让你改。并入走"路径 A"，新建走"路径 B"。

4. 做"收尾自检"，然后跳到 Step 4，总结里写清楚改了哪篇的哪一节、改了什么。

## 路径 B：新文章

### Step 0：封面去重

封面不能与其他文章重复，以压缩后的文件内容 MD5 为准。候选图要先用和封面相同的参数压缩再比对，原图的哈希永远对不上已压缩的封面。壁纸目录里 jpg 和 png 都要考虑：

```bash
cd /Users/baizhe/code/github/blog-source
TMP=$(mktemp -d)

# 1. 已用封面的哈希集合（含 banner.jpg，避免和首页主题图重复）
for f in source/img/banner.jpg source/img/p*.jpg; do md5 -q "$f"; done | sort -u > "$TMP/used.txt"

# 2. 逐个候选：压缩一遍和压缩两遍的哈希都比对，都不在集合里才算没用过
for w in ~/Pictures/wallpaper/*; do
  case "$w" in *.jpg|*.jpeg|*.JPG|*.png|*.PNG) ;; *) continue ;; esac
  cp "$w" "$TMP/c.jpg"
  sips -s format jpeg -s formatOptions 80 -Z 1920 "$TMP/c.jpg" >/dev/null 2>&1; h1=$(md5 -q "$TMP/c.jpg")
  sips -s format jpeg -s formatOptions 80 -Z 1920 "$TMP/c.jpg" >/dev/null 2>&1; h2=$(md5 -q "$TMP/c.jpg")
  grep -q -e "$h1" -e "$h2" "$TMP/used.txt" || echo "未使用: $w"
done
```

挑一张看一眼，选画面里没有游戏、品牌 logo 或版权水印的，复制到 `source/img/pXX.jpg`（XX 为当前最大编号 +1）并压缩：

```bash
sips -s format jpeg -s formatOptions 80 -Z 1920 source/img/pXX.jpg
```

完成标准：`pXX.jpg` 的 MD5 不在 `used.txt` 里。

本地壁纸都用过了，就按 CLAUDE.md 的备选来源从 uhdpaper.com 找。直接 curl 会因防盗链拿到 HTML，要带 `-e <详情页地址>`（Referer）和 `-A <浏览器 User-Agent>`。

### Step 1：写作计划

调用 `superpowers:writing-plans`，确定文章类型（教程/工具介绍/深度解析）、主要章节和每节核心内容、读者定位和篇幅。

计划文件写到 `~/.claude/plans/`，文件名 `YYYY-MM-DD-文章主题.md`，不进仓库。

### Step 2：写作

写作规范以 CLAUDE.md 为准。这里补充两点：

- 教程类按"基础操作 → 原理机制 → 使用场景"组织，速查类用分类标题加编号列表。
- 写完回到相关的已有文章里加互相链接，并更新它们的 `updated`。

### Step 3：用四个 skill 优化

依次调用：
1. `technical-blog-writing`：技术博客标准，代码是否可运行、表述是否准确
2. `blog-writing-guide`：开头是否直接切入、标题是否传递信息、有无 AI 套话
3. `seo-content-writer`：description 字段、H2 关键词覆盖
4. `content-quality-auditor`：结构完整性、可读性、事实声明是否有据

发现问题直接修改，改完在总结里一并交代。

### Step 3.5：准确性与时效性核查

完成标准：文章里每条具体的技术声明（版本号、命令和参数、API 和配置字段、安装方式、外部链接）都核对过，核对依据是官方文档或实际运行。

- 核实无误：保持原样。
- 过时或有误：直接改，总结里注明改了什么。
- 无法核实：文中加注"建议以官方文档为准"或标明版本适用范围。
- 灵感来自会话里的口头结论时，把它当作待验证的假设，对着官方文档或运行结果核对。当时讲错了，在总结里如实告诉我。

## 收尾自检（两条路径都做）

1. `date`、`updated` 字段用 `date "+%Y-%m-%d %H:%M:%S"` 的真实输出。
2. 用 BLOG 自带的 `marked` 渲染整篇，代码块之外没有残留的字面 `**`。加粗紧贴反引号代码块、或加粗里含直角引号 `"`，都会渲染失败，改成全角引号或把代码挪到加粗外。
3. 新文章里的互相链接指向存在的文章。
4. 正文的引号用中文引号“ ”，连续引用几个词时中间加顿号（“自动”、“当前”）。ASCII 直角引号在页面上会显示成别扭的 ″。代码块和 HTML 属性里的引号不动。
5. 站在读者视角通读一遍：不写作者自己的工具、网络和检索过程（“我这台机器连不上”“我搜到的”）。来源和可靠程度用客观的话说清楚，例如“数字来自官方博客，操作路径没有对照官方帮助页逐步核实”。
6. 站内链接写成 `<a href="/文件名#小节标题" target="_blank" rel="noopener">文字</a>`，新标签页打开并直达小节。锚点是标题原文，空格换成 `-`，写之前去已渲染的页面确认 id。

## Step 4：起公网预览地址，停下来等我审核

**先清理残留进程**（比如我之前手动起过、忘了关）：
1. `lsof -ti:4000`，有 PID 就 `kill`，并告诉我"检测到旧的 hexo server 还在跑，已停止"。
2. `pgrep -fl "tailscale funnel"` 查 funnel（用 pgrep：前台模式的 funnel 不会出现在 `tailscale funnel status` 里）。macOS 上 Tailscale.app 的 CLI 是包装脚本，会跑出父子两个进程，匹配到几个 PID 就全部 `kill`，只杀一个会留下孤儿进程继续占着公网暴露。杀完告诉我"检测到旧的 Tailscale funnel 还在跑，已停止"。

**确认干净后启动**（都在 BLOG 目录下）：
1. 后台启动本地预览：`hexo clean && hexo server`
2. 前台模式代理到公网：`tailscale funnel 4000`（不加 `--bg`，配置跟这个进程绑定）
3. 取到公网地址，过程和原始输出不用展示。

完成标准：文章的公网直达链接 `curl` 返回 200。

**总结**按这个顺序写，公网地址放在最后（手机翻看时往上翻很不方便）：
- 路由结论：并入了哪篇哪一节，或新建了文章，以及理由和备选
- 文件路径
- 文章结构（各章节标题）；并入的话写清楚改了哪一节、改了什么
- 核实时发现的问题（比如会话里当时讲错的地方）
- 还可以扩展的方向（可选）
- 公网预览地址：总结的最后一项，单独一行只放这个 URL，后面不接任何文字（连在一起会被识别成同一个打不开的链接）。补充说明放在 URL 前面。URL 给到具体文章的直达链接（`https://域名/文章路径/`）；一次交付多篇，每篇的直达链接各占一行。

总结末尾问一句：审核完成后告诉我一声。然后停下来等我。

收到"停掉"：直接终止 `hexo server` 和 `tailscale funnel` 两个进程，前台模式下进程退出会自动清掉公网暴露。
